# Distributed Task Queue

Асинхронная очередь задач с HTTP API, пулом воркеров и персистентным хранилищем на PostgreSQL.
Проект учитывает частичные отказы (компенсирующий статус при сбое публикации, graceful shutdown) и явно фиксирует
границы консистентности (см. ограничения).

Проект в активной разработке.

---

## Технологии

- **Language:** Go 1.22+ (`net/http` с роутингом, `log/slog`, `sync`, `context`)
- **Database:** PostgreSQL (драйвер `jackc/pgx/v5`, сырой SQL без ORM)
- **Infrastructure:** Docker & Docker Compose (для локального окружения)
- **Kafka, gRPC, Prometheus/OpenTelemetry** — в планах, не начаты

---

## Архитектура

Два бинарника, спроектированных как независимые процессы, которые общаются только через Postgres и брокер сообщений.

### Компоненты системы

Система разделена на два независимых домена (бинарника):

- `cmd/api` — HTTP-сервер. Принимает задачи, сохраняет их состояние и отдает текущий статус клиенту.
- `cmd/worker` — Обработчик. Получает задачи из очереди, выполняет бизнес-логику и обновляет статус в БД.

### Архитектурные решения и компромиссы

На текущем этапе интеграция внешней очереди сообщений (Kafka/RabbitMQ) находится в планах, поэтому архитектура
адаптирована под временный монолитный запуск без потери модульности.

1. **In-Memory Broker:** Для оркестрации задач используется внутренняя реализация `InMemoryBroker`;
2. **Монолитный запуск:** Поскольку `InMemoryBroker` изолирован в рамках одного процесса, пул воркеров (`cmd/worker`)
   инициализируется и запускается внутри процесса `cmd/api`;
3. **Слабая связанность (Loose Coupling):** Компоненты `Pool` и `Handler` зависят исключительно от интерфейсов `Broker`
   и `Repository`. Переход на внешний брокер должен затронуть в основном main.go и новую реализацию Broker.
   Совместимость интерфейса с семантикой Kafka ещё предстоит проверить;
4. **Граница API и воркеров:** HTTP-слой намеренно не валидирует `Type` задачи по реестру хендлеров.
   Это изолирует контекст API от контекста воркеров, позволяя деплоить и масштабировать их независимо.

### Структура проекта

Дизайн пакетов представляет собой нестрогую чистую архитектуру без избыточного Usecase-слоя:

```
internal/
├── domain        — Доменные модели (Task, статусы)
├── broker        — Интерфейс Broker и его in-memory реализация
├── storage       — Интерфейс Repository и реализация слоя доступа к PostgreSQL
├── worker        — Реестр хендлеров и логика пула воркеров (Worker Pool)
├── api/http      — HTTP-хендлеры, DTO, маршрутизация
└── config        — Загрузка конфигурации окружения (env)
```

## Что реализовано

### 1. Доменная модель (Domain)

- **Сущность `Task`:** Содержит `ID`, `Type`, `Payload` (`json.RawMessage`), `Status`, `RetryCount`, `MaxRetries`, метки
  времени и расписание.
- **Жизненный цикл:** Поддерживаются статусы `pending`, `done`, `failed` и компенсирующий статус `queue_failed` (задача
  сохранена в БД, но произошел сбой отправки в брокер). По умолчанию `MaxRetries = 3`.

### 2. Очередь сообщений (Broker)

Интерфейс `Broker` (`Publish` / `Subscribe` / `Ack` / `Nack`) и `InMemoryBroker` на мьютексе и буферизованном канале:

- `Publish` — ранняя проверка `ctx.Err()` до `select`/`default`, чтобы избежать гонки выбора;
- `Subscribe` — запись в `pending`-мапу происходит **до** отправки в канал (happens-before), иначе возможна гонка с
  `Ack`;
- `Ack` — удаление из `pending` (успешный сценарий);
- `Nack` — удаление из `pending` и возращение задачи обратно в очередь, если не исчерпаны все попытки выполнения;
  `failed=true` — провал после всех повторных попыток, `failed=false` — задача ушла на retry без обращения к БД.

Покрыт тестами, включая конкурентный сценарий.

### 3. Хранилище (Storage)

Интерфейс `Repository` (`Create` / `GetByID` / `UpdateStatus`, `ErrNotFound`) и `postgres.Repository` поверх `pgxpool`

- Используется чистый SQL и ручной маппинг строк.

Покрыт интеграционными тестами через `testcontainers-go`.

### 4. Пул воркеров (Worker Pool)

- **Реестр хендлеров:** Явная регистрация обработчиков с защитой от дублирования типов (паника при инициализации);
- **Изоляция контекстов:** Воркер обрабатывает задачу в изолированном `context.Background() + TaskTimeout`. Это
  гарантирует, что Graceful Shutdown приложения не прервет запущенную работу воркера;
- **Консистентность статусов:** Соблюдается строгий порядок: сначала `UpdateStatus` в БД, затем `Ack` в брокере;
- Если для типа задачи отсутствует хендлер, она сразу переводится в статус `failed`, минуя механизм повторных попыток.

### 5. HTTP API

`POST /tasks` — валидирует запрос, сохраняет задачу в Postgres, публикует в брокер, отвечает `202 Accepted`.
`GET /tasks/{id}` — отдаёт текущее состояние запрошенной задачи.

- **Безопасность данных:** Реализован middleware для логирования и восстановления в случае паники кода. Тело
  запросов/ответов намеренно не логируется во избежание утечки чувствительных данных;
- **Инкапсуляция ошибок:** Любые внутренние сбои (инфраструктура, БД) маскируются. Клиент получает стандартный
  текст ошибки, детали реализации и логи не попадают наружу;
- **Парсинг:** Включена опция `DisallowUnknownFields` при декодировании JSON. Необязательные поля заполняются дефолтными
  значениями, затем происходит валидация запроса.

Компонент покрыт тестами на валидацию, граничные случаи и логику обработки сбоев.

### 6. Конфигурация (Config)

- Парсинг переменных окружения из `.env` файла реализован на чистом Go с поддержкой кавычек и инлайн-комментариев.
  Не перезаписывает уже установленные системные переменные;
- Паникует на этапе инициализации (`Load`) при некорректной конфигурации;
- Покрыт тестами, включая проверку корректности маппинга переменных к полям структуры `Config`.

## Контракт API

- **Асинхронная обработка:** Статус `202 Accepted` гарантирует только валидацию DTO и фиксацию задачи в системе, но не
  наличие зарегистрированного хендлера или успешную обработку;
- **Обработка неизвестных типов задач:** Ошибки неизвестных типов выявляются асинхронно на стороне воркера.
  Задача переводится в статус `failed` без повторных попыток выполнения;
- **Частичные отказы (Dual-Write):** Если задача успешно записана в PostgreSQL, но не опубликована в брокер (например,
  переполнен буфер), клиент получает ответ `202` со статусом `queue_failed`;
- **Маршрутизация:** Метод `GET /tasks/{id}` возвращает `404 Not Found` для несуществующих ID.

## Остановка (graceful shutdown)

По SIGINT/SIGTERM остановка идёт в следующем порядке:

1. HTTP-сервер перестаёт принимать запросы и дожидается выполнения текущих;
2. Воркеры перестают брать новые задачи и дорабатывают начатые (не дольше `WORKER_TASK_TIMEOUT` + 1s).
3. Закрывается пул соединений с Postgres.

В логах это выглядит так:

```
shutdown signal received → http stopped → worker pool stopped → database connection closed
```

Если сервер не смог стартовать (например, порт занят), остановка проходит тем же путём, а процесс завершается с кодом 1.
Штатная остановка по сигналу даёт код 0.

Второй сигнал во время остановки завершает процесс немедленно, без ожидания воркеров.

## Архитектурные ограничения и компромиссы

Текущие ограничения системы обусловлены использованием in-memory брокера на этапе MVP и будут устранены при переходе на
постоянную инфраструктуру.

- **Зависимость от жизненного цикла процесса:** Поскольку `InMemoryBroker` хранит состояние в оперативной памяти, задачи
  в буфере брокера не переживают рестарт приложения. При перезапуске они остаются в PostgreSQL в статусе `pending` и
  требуют фонового восстановления;
- **Ограничение Graceful Shutdown:** Повторный (принудительный) сигнал `SIGINT/SIGTERM` прерывает выполнение текущих
  воркеров. Запущенные задачи могут остаться незавершенными до момента их обработки механизмом восстановления;
- **Жизненный цикл ретраев:** Счетчик повторных попыток (`RetryCount`) на данном этапе инкрементируется только в памяти
  брокера и сбрасывается при перезапуске процесса;
- **Отложенное выполнение (`ScheduledAt`):** Поле сохраняется в БД, но логика задержки публикации (`Delay Queue`) в
  текущей реализации брокера и пула воркеров не активирована;
- **Абстракция восстановления (Recovery Process):** Компонент фонового восстановления сформулирован, но ещё не
  имплементирован. Для его корректной работы требуется внедрение промежуточного статуса `processing` и фиксация времени
  взятия задачи в работу (`PickedUpAt`) для обнаружения зависших тасок по тайм-ауту;
- **Паттерн Outbox отложен:** Паттерн Transactional Outbox сознательно не реализуется поверх in-memory очереди, так как
  гарантия доставки (*at-least-once*) имеет смысл только при наличии долговечного (durable) брокера (Kafka/RabbitMQ).
  Развертывание Outbox отложено до интеграции с шиной данных;
- **Идемпотентность:** На текущем этапе ответственность за идемпотентность обработки (предотвращение дубликатов)
  возложена на вызывающий код и логику самих хендлеров.

- **Юнит-тестирование:** Пакеты `broker`, `worker` и `api/http`;
- **Интеграционное тестирование:** Логика работы слоя `storage/postgres` вынесена в изолированные `_test`-пакеты. Для

  отсутствия состояний гонки (Race Conditions).

## Запуск

Для локального запуска требуется установленный Docker (с Docker Compose) и Go версии 1.22+.

```bash
docker-compose -f deployments/docker-compose.yml up -d postgres
psql "postgres://taskqueue:taskqueue@localhost:5432/taskqueue?sslmode=disable" -f migrations/0001_init_tasks.up.sql
go run ./cmd/api
```

`export POSTGRES_CONN_STRING="postgres://taskqueue:taskqueue@localhost:5432/taskqueue?sslmode=disable"` или .env

`go run ./cmd/api` поднимает API и worker pool вместе (см. «Архитектура»). Отдельно запускать `cmd/worker` сейчас не
нужно.

Полный `docker-compose` (api + postgres) — в планах.

### Конфигурация

Переменные окружения или файл `.env` в рабочей директории:

| Переменная                | По умолчанию | Описание                             |
|---------------------------|--------------|--------------------------------------|
| `POSTGRES_CONN_STRING`    | обязательна  | DSN Postgres                         |
| `BROKER_BUFFER_SIZE`      | `100`        | размер буфера брокера                |
| `POOL_NUM_WORKERS`        | `5`          | число воркеров                       |
| `WORKER_TASK_TIMEOUT`     | `30s`        | таймаут обработки одной задачи       |
| `API_ADDR`                | `:8080`      | адрес HTTP-сервера                   |
| `API_READ_HEADER_TIMEOUT` | `5s`         | таймаут чтения заголовков            |
| `API_READ_TIMEOUT`        | `10s`        | таймаут чтения запроса               |
| `API_WRITE_TIMEOUT`       | `10s`        | таймаут записи ответа                |
| `API_IDLE_TIMEOUT`        | `60s`        | таймаут простаивающего соединения    |
| `API_SHUTDOWN_TIMEOUT`    | `15s`        | ожидание HTTP-запросов при остановке |

Невалидное значение приводит к panic при старте. Подключение к Postgres проверяется `Ping` с тайм-аутом 10 секунд: если
БД недоступна, процесс завершается.

## Пример API

В демо зарегистрирован один тип задачи — `demo` (заглушка, ждёт 3 секунды).

```bash
curl -X POST localhost:8080/tasks \
  -H "Content-Type: application/json" \
  -d '{"type": "demo", "payload": {"message": "hello"}}'
# → 202 {"id": "...", "status": "pending"}

curl localhost:8080/tasks/{id}
# через ~2s → 200 {"id": "...", "type": "demo", "status": "done", ...}

# неизвестный тип: API принимает, обработка завершается статусом failed
curl -X POST localhost:8080/tasks \
  -H "Content-Type: application/json" \
  -d '{"type": "unknown", "payload": {}}'
# → 202 {"id": "...", "status": "pending"}, затем GET → "status": "failed"
```
